# Week 12: four pillars of OOP

Upload `Java2_Week_12.codeshare.json` to the intended class after the sample-first app and its
history migration are installed. Its stable module id is `java-2-w12`. Upload Weeks 12, 13 and
14 in that order. These are new JSON files; the original printed modules and lesson plans
have not been edited.

**Work in code editor** loads each complete sample on first opening. Run it unchanged to save
**Sample verified**, then make the small change under **Your task**. Matching **Expected task
output** saves **Completed** immediately and unlocks the next activity. Reopening a step restores
its saved edits. Paper liplets are assessed separately and never block progress.

The printed OOP module uses three catch-up sessions, while its ILAW plan spans five days.
The JSON retains the printed sequence in five consecutive parts: encapsulation, inheritance,
polymorphism, abstraction and synthesis. It uses DAY 1, DAY 2 and DAY 3 rather than inventing
Monday–Friday dates. Definitions, analogies, private-field and abstract-class compiler examples,
liplets and the separate personal performance task are included.

Each step supplies all Java classes it needs. Deliberately uncompilable examples remain reading
experiments; they do not prevent required sample runs. The final abstract Vehicle, Jeepney,
Tricycle and Bus classes roll into Week 13, where capacities and exceptions are added.

Module-level `starterFiles` is empty: module samples come from each step. This prevents the
module's Vehicle family from being inserted into a new personal performance project. Personal
starters contain only Main.java guidance, and students build their own theme. The two projects,
previous weeks and submitted versions remain separate. Solved alterations are test fixtures only.

All nine samples and nine alterations are checked with real laptop Java and browser Java 8;
the complete evidence and limits are in [verification](../../verification/week12-week13-modules.md).
The generation prompt/playbook and original PDF/DOCX revisions remain separate work.

Revised exercises test object state, inherited behavior, dispatch or error paths rather than renaming output text. Changed requirements have new `-v2` task identities: earlier results remain stored and cannot pass the new exercise. The displayed source remains the unsolved sample.
